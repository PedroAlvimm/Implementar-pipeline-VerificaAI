# VerificaAI 1.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar o VerificaAI 1.0 como aplicação Django local, com pipeline factual auditável por `AnalysisRun`, executor em memória, BERTimbau auxiliar, SQLite e artefatos no filesystem.

**Architecture:** Django será a única camada web e de persistência. Um executor local limitado executará o pipeline existente contra modelos Django; o resultado factual será concluído antes da análise BERT auxiliar, e reinícios transformarão runs ativos em falhas recuperáveis por reexecução manual.

**Tech Stack:** Python 3.12+, Django 5.2 LTS, Django REST Framework 3.16+, SQLite, templates Django, `concurrent.futures`, Pydantic 2, Transformers/PyTorch opcionais e pytest/pytest-django.

**Spec:** `docs/superpowers/specs/2026-10-06-verificaai-1-0-simplified-design.md`

**Substitui:** os planos `2026-10-06-verificaai-django-foundation.md`, `2026-10-06-verificaai-django-runtime.md` e `2026-10-06-verificaai-django-web-cutover.md`.

## Global Constraints

- Django é o único framework web; FastAPI, Streamlit e SQLAlchemy permanecem apenas até o cutover da Tarefa 5.
- `AnalysisRun` nunca é reutilizado ou sobrescrito; toda reexecução cria novo ordinal.
- Não criar `Job`, fila persistida, lease, heartbeat, Celery, Redis ou retry de run.
- SQLite opera em um único processo web e baixa concorrência, com WAL, foreign keys e busy timeout.
- HTML e artefatos volumosos ficam no filesystem; o SQLite guarda somente metadados e resultados estruturados.
- BERTimbau é auxiliar, não participa de retrieval/ranking e nunca altera ou impede o veredito factual.
- SSRF deve ser bloqueado em cada resolução DNS e redirecionamento; falha de `robots.txt` não concede permissão.
- Indisponibilidade técnica não pode ser representada como ausência de evidência.
- Toda citação aceita deve existir literalmente no trecho normalizado persistido.
- Testes não acessam rede real; o smoke test do bucket Hugging Face permanece opcional e separado.
- Não iniciar executores em imports, migrations, comandos de management ou testes que não os solicitem.
- As alterações parciais não commitadas em `analyses/models/` são material de trabalho: reaproveitar apenas o que coincide com a spec e remover o modelo `Job`.

## Review Focus

- Ambiente herdando outro `DJANGO_SETTINGS_MODULE`: testes devem continuar fixados em `verificaai.settings.test` (Tarefa 1).
- Duas reexecuções concorrentes da mesma análise: apenas uma pode criar o próximo run ativo (Tarefa 1).
- Citação com normalização de espaços/Unicode, mas texto diferente: deve ser rejeitada, não aproximada (Tarefa 2).
- BERT bloqueado ou inválido depois do fact-check: o run factual continua concluído e consultável (Tarefa 3).
- Reinício com runs `QUEUED` e `RUNNING`: ambos viram `FAILED/PROCESS_INTERRUPTED` sem alterar runs terminais (Tarefa 3).

- `analyses/management/commands/import_legacy_sqlite.py`: importador transacional e idempotente.

## Whole-branch Review

Após as cinco tarefas, um revisor independente deve comparar todo o diff com a spec, executar a
verificação final e procurar especialmente: dependências/entrypoints antigos restantes, threads
criadas em import, caminhos de artefato inseguros, resultados BERT influenciando o veredito,
citações não literais e qualquer tratamento de falha técnica como ausência de evidência.
